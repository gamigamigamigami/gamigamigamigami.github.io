Claude Code サブエージェントの作り方｜呼ばれない・結果が返らないを直す

サブエージェントの定義ファイルを置いたのに、何も起きない。名前を呼んでも見つからない。動いたように見えても、返ってくる内容が薄い。どれも似ていますが、確認するところは同じではありません。この記事では、サブエージェントを一つ作り、名前を指定して呼び、結果を受け取るところまで進めます。

すでに.claude/agents/へMarkdownファイルを置いた人も、同じ順番で確認します。「名指ししても見つからない」「名指しなら動くが自動で呼ばれない」「呼ばれるが空振りする」は、原因がそれぞれ違います。表示されるか、名前を指定すれば動くか、自動で選ばれるか、返ってきた内容を確かめられるか。この順で見ていきます。

この記事が扱うのは「動かないサブエージェントの直し方」まで

最初に知っておきたいのは、サブエージェントの挙動は定義ファイル1枚だけでは決まらないことです。ファイルの置き場所と書式が合って初めて名指しで呼べます。呼び出せたあと、使える道具と依頼文によって結果が変わります。一度に五つを調整するのではなく、この前後関係に沿って一つずつ確認します。

やっかいなのは失敗の出方です。どれか1つが外れても、赤いエラーが出るわけではありません。静かに何も起きない、あるいは何となく動いているように見えて中身が薄い、という形で現れます。だから手順記事を何度読み直しても原因にたどり着けません。

この記事では、その五つを一度に直そうとせず、画面と出力を見ながら一つずつ確認します。扱うのはCLIとVS Codeで動かした場合の差分までです。Agent SDKで別のエージェントを実装する話は含めません。

サブエージェントは、別の会話として動きます

サブエージェントは、メインとは独立したコンテキストウィンドウで動きます。「別の担当者」のような比喩ではなく、本当に会話の中身が分かれています。

つまり、メインの会話でどれだけ丁寧にやり取りしていても、通常のサブエージェントはその会話履歴を見ていません。読み込まれるCLAUDE.mdなどのプロジェクト指示はありますが、直前に貼ったエラーログや、その場で説明した条件は自動では渡りません。委任時の依頼文へ必要な情報を含めます。

そして終了時にも、作業の中身はメイン側に戻りません。戻ってくるのは最終的な報告テキスト1通で、途中で読んだファイルも試した手順も、メインのコンテキストには積まれない仕組みです。「コンテキストを汚さない」と言われるのは、この一方通行の構造を指しています。

この仕組みには、よい面と面倒な面があります。大量のファイルを読む調査を別の会話へ任せられる一方で、依頼に必要な情報は毎回渡さなければなりません。そのため、短い説明で仕事が完結するものには向きますが、相談しながら決めたい仕事には向きません。

なお、サブエージェントと Agent Teams は別の機能として提供されています。どちらも複数の AI が動く点は同じですが、前者は1つのセッションから呼び出す下請けで、後者は別の枠組みです。混同すると「並列で動くはずなのに動かない」という誤解につながります。

最初に使う4フィールドは、別々の役割を持っています

定義ファイルはYAMLフロントマター付きのMarkdownです。最初に使うのはname、description、tools、modelの4つで、このうち必須なのはnameとdescriptionです。現在はほかにも権限モード、最大ターン数、Skills、MCP、メモリ、バックグラウンド実行などを指定できますが、最初の一つを動かす段階では使いません。フロントマターより下の本文が、そのサブエージェントのシステムプロンプトになります。

description が担当するのは「呼ばれるかどうか」です。メインの Claude は、あなたの依頼文と各サブエージェントの description を突き合わせて委任先を決めます。ですから「コードをレビューします」のように短く曖昧だと、判断材料が足りずに呼ばれません。自動で呼ばれない症状の原因は、ほぼここに集中します。

tools が担当するのは「呼ばれた後に何ができるか」です。この行を書かなければ、MCP のツールを含めて利用可能なツールをすべて継承します。逆に書いた場合は書いたものだけになるので、ここで Read や Grep を落とすと、レビュー用のはずのサブエージェントがファイルを1つも読めず、一般論だけを返してきます。

model は「どのモデルで走るか」です。指定しなければ設定に従うため、調査系だけ軽いモデルに寄せる、といった使い分けができます。ただし難しい判断を任せる役に軽いモデルを当てると、報告の質はその分落ちます。

name は「名指しで呼べるかどうか」を決めます。小文字とハイフンで書く決まりなので、日本語や大文字を混ぜると名指しの委任が通らなくなります。

本文（システムプロンプト）に書くべきなのは、人格設定ではありません。相手は文脈をまったく持っていないので、何を確認し何を確認しないか、どういう形式で報告するかを書かないと、報告の粒度が毎回ぶれます。

「呼ばれない」「空振りする」が起きる、仕組み上の理由

症状は大きく3つに分かれます。①名指ししてもサブエージェントが見つからない、②名指しでは動くが自動で呼ばれない、③呼ばれるが報告が薄い。原因はそれぞれ違うので、対処も別々になります。

①はファイルが読み込まれていない状態です。原因の多くは置き場所の間違いか、YAMLの書式エラーです。descriptionにコロンを含む文章を書くなら、値全体を引用符で囲みます。読み込みに失敗した理由は、通常画面だけで分からなければデバッグログで確認します。

②は description の情報不足です。委任の判断はその文面だけを見て行われるので、「いつ使うか」が書かれていなければ判断のしようがありません。

③はコンテキスト分離が原因です。メインの Claude が「レビューして」とだけ書いて委任すると、サブエージェント側は対象ファイルも判断基準も知らないまま作業を始めます。その結果、返ってくるのは当たり障りのない一般論になります。

ここまでが原因の説明です。以降の有料部分では、①〜③をそれぞれ特定して直す手順を扱います。

  • 置き場所を決める：プロジェクト用とユーザー用、どちらに置くか
  • 名前を指定して呼び出す：定義が読まれているかを確かめる
  • tools の書き方：ツール名は正確な文字列で、大文字小文字も一致させる
  • claude コマンドから実行する：対話に左右されない確認方法
  • tools と permissions は別レイヤー：コマンド実行の許可が通らない理由
