VSCodeでのClaude Codeの使い方｜拡張機能の導入からSkillsまで

「VSCodeでClaude Codeを使う」は、実は3つの別々の部品の話

拡張機能を入れたのに何も起きない、という状態でこのページに来た方が多いはずです。

先に結論を言うと、それは手順を間違えたからではありません。Claude Code が VS Code の拡張機能そのものではないからです。

本体は、ターミナルで動く claude という名前のコマンドラインプログラム。拡張機能はその本体を VS Code 側から見えるようにする受け口であって、本体の代わりではありません。

この前後関係を取り違えると、以降の作業がすべてずれます。

必要な部品は3つ。(1) claude 本体、(2) VS Code 拡張機能「Claude Code for VS Code」、そして (3) その2つを繋ぐ接続です。3つ目が独立して存在する、というのがこの記事の中心になる話です。

拡張機能を入れる作業は (2) を満たすだけであって、(1) と (3) には手を付けていません。

接続が成立しているかどうかは、体感ではなく表示で分かります。CLI 側で /ide を実行したときに接続先の IDE 名が出るか、/status に IDE の項目が出るか。ここが空なら、拡張機能が入っていても「入っているだけ」の状態です。

接続が成立したときに変わることも、具体的に決まっています。編集提案がエディタの差分ビューとしてタブで開き、VS Code で選択している範囲が自動で文脈に入り、Problems パネルに出ている Lint エラーや型エラーが Claude 側から見えるようになる。この3つが起きていなければ、繋がっていません。

一次情報は公式の IDE integrations にあります。

なぜ「拡張機能を入れたのに何も起きない」が起きるのか

Marketplace から拡張機能を入れれば使える、という手順は多くのツールで完結します。しかし Claude Code の拡張機能は本体を同梱していないので、本体が無ければ起動する対象が存在しません。ここで止まっている場合、VS Code の画面をいくら探しても原因は見つかりません。

具体的には、拡張機能一覧で Claude Code が有効になっていても、ターミナルで claude --version がバージョンを返さない限り、拡張機能が呼び出す先そのものが存在しないということです。

逆のパターンもあります。CLI を先に入れて統合ターミナルで claude を起動すると、拡張機能は自動で導入される経路があるためです。入手ルートは「Marketplace で手で入れる」「ターミナルから起動して自動で入る」の2つ。どちらを通ったかで、次に確認すべき場所が変わります。

3つ目の落とし穴は、起動した場所。

VS Code の統合ターミナルで起動した claude は、自分が VS Code の中にいることを環境変数から検知できます。iTerm2 や Windows Terminal のような外部のターミナルで起動した claude は、同じマシンで VS Code が動いていても自動では繋がりません。これが「Mac だと繋がるのに Windows だと繋がらない」と誤解されがちな箇所で、実際の原因は OS ではなく起動場所、という場合が少なくありません。

ここまでを整理すると、失敗は3つの層に分かれます。インストール層（claude が PATH に無い）、接続層（拡張機能と CLI が握手していない）、権限層（動いてはいるが毎回確認され続けて作業が進まない）。自分の症状がどの層のものかを見分けられれば、対処は機械的に決まります。

Cursor や Windsurf のような VS Code 派生エディタでも仕組みは同じですが、拡張機能の入手元が異なります。派生エディタを使っているなら、まずこの層のズレを疑ってください。

Mac・Windows・WSL で変わるのは「どこ」なのか

OS で変わるのは主にインストール方法と PATH の通り方であって、接続の仕組みも使い方も共通です。「Mac 前提の記事しか無い」と困る必要はなく、差分がある箇所だけを押さえれば足ります。

Mac と Linux は比較的単純で、公式インストーラか npm 経由（npm install -g @anthropic-ai/claude-code）のどちらか。npm を選ぶと Node.js のバージョン要件が乗ってくるうえ、グローバル install の権限エラーという別問題も発生しえます。

Windows の分岐は、ネイティブで動かすか WSL の中で動かすか。この選択が後から効いてきます。

WSL を選ぶと、VS Code 側の拡張機能も WSL 側にインストールされている必要が生じるためです。ローカルに入れた拡張機能は、WSL のプロジェクトからは見えません。ネイティブを選んだ場合は、Claude Code が内部で Git Bash を使う場面があるので、Git for Windows が入っていない、あるいは非標準の場所に入っていると固有のエラーになります。

一方で .claude/skills/ や CLAUDE.md といったプロジェクト側のファイルは OS に依存しません。一度環境を作ってしまえば、Mac と Windows で同じリポジトリを同じ設定のまま使えます。

ここから先で扱うこと

ここまでが「何が起きているか」の説明でした。以降は実際の手順に入ります。

有料部分は、コマンドと確認方法をそのまま実行できる粒度で書き、各手順に「これが表示されたら成功」という判定条件を付けているので、途中で止まった位置を特定できます。すでに導入済みで「繋がらないだけ」の人は、切り分け手順から読んでも成立する構成にしました。

  • Mac：インストールから「接続済み」の表示が出るまで
  • Windows：ネイティブか WSL か、判断基準と手順
  • 権限モードと settings.json：毎回の確認を減らす
  • Skills を VS Code で使う：置き場所と、呼ばれる条件
  • 繋がらない・動かないときの切り分け手順
