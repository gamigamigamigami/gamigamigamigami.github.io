# Claude Code サブエージェントが動かないときの直し方

Claude Code でサブエージェントを作る手順そのものは、もう多くの記事に書かれています。それを読んで .claude/agents/ に Markdown ファイルを置いたのに、自動では呼ばれない、名指しで呼んでも当たり障りのない報告しか返ってこない、VS Code で開くと一覧にすら出てこない——この記事は、そこで止まっている方に向けて書きます。

この記事が扱うのは「動かないサブエージェントの直し方」まで

まず前提を共有します。サブエージェントの挙動は、定義ファイル1枚では決まりません。実際に効いているのは、ファイルの置き場所、YAML フロントマターの書式、tools の記述、settings.json の permissions、そして委任するときに渡す依頼文の5つで、これらが噛み合って初めて期待どおりに動きます。

やっかいなのは失敗の出方です。どれか1つが外れても、赤いエラーが出るわけではなく、静かに何も起きない、あるいは何となく動いているように見えて中身が薄い、という形で現れます。だから手順記事を何度読み直しても原因にたどり着けません。

この記事では、その5つの依存関係を分解して、自分の環境のどこが外れているかを特定できるところまで持っていきます。参照するのは公式ドキュメントの Subagents と Settings です。扱う範囲は CLI と、VS Code で動かした場合の差分までとし、Agent SDK でエージェントを実装する話は含めません。

サブエージェントの実体は「使い捨ての別セッション」です

公式ドキュメントは、サブエージェントを独立したコンテキストウィンドウを持つ特化型のアシスタントとして説明しています。

ここで大事なのは「独立した」の部分です。これは分かりやすくするための比喩ではなく、そのままの仕様です。つまり、メインの会話でどれだけ丁寧にやり取りしていても、サブエージェント側はそれを一切見ていません。あなたが説明したディレクトリ構成も、直前に読ませたエラーログも、向こうには存在しない情報で、渡されるのはメインの Claude がそのとき書いた依頼文だけになります。

そして終了時にも、作業の中身はメイン側に戻りません。

戻ってくるのは最終的な報告テキスト1通で、途中で読んだファイルも試した手順も、メインのコンテキストには積まれない仕組みです。「コンテキストを汚さない」と言われるのは、この一方通行の構造を指しています。

ここから利点と弱点が両方導けます。利点は、大量のファイルを読む調査を丸ごと別セッションに追い出せることです。一方で弱点は、前提の共有コストが毎回かかることで、そのため短い依頼文で自己完結する仕事ほど向いていて、あなたと相談しながら詰めていく仕事ほど向きません。

なお、サブエージェントと Agent Teams は別の機能として提供されています。どちらも複数の AI が動く点は同じですが、前者は1つのセッションから呼び出す下請けで、後者は別の枠組みです。混同すると「並列で動くはずなのに動かない」という誤解につながります。

定義ファイルの4フィールドは、別々の失敗を担当しています

定義ファイルは YAML フロントマター付きの Markdown で、フロントマターに書けるのは name / description / tools / model の4つです。加えて、フロントマターより下の本文がそのままシステムプロンプトになります。この4つは役割がきれいに分かれていて、どれが欠けているかで症状が変わります。

description が担当するのは「呼ばれるかどうか」です。メインの Claude は、あなたの依頼文と各サブエージェントの description を突き合わせて委任先を決めるので、「コードをレビューします」のように短く曖昧だと、判断材料が足りずに呼ばれません。自動で呼ばれない症状の原因は、ほぼここに集中します。

tools が担当するのは「呼ばれた後に何ができるか」です。この行を書かなければ、MCP のツールを含めて利用可能なツールをすべて継承します。逆に書いた場合は書いたものだけになるので、ここで Read や Grep を落とすと、レビュー用のはずのサブエージェントがファイルを1つも読めず、一般論だけを返してきます。

model は「どのモデルで走るか」を決めます。指定しなければ設定に従うため、調査系だけ軽いモデルに寄せる、といった使い分けができますが、難しい判断を任せる役に軽いモデルを当てると、報告の質はその分落ちます。

name は「名指しで呼べるかどうか」を決めます。小文字とハイフンで書く決まりなので、日本語や大文字を混ぜると名指しの委任が通らなくなります。

本文（システムプロンプト）に書くべきなのは、人格設定ではありません。相手は文脈をまったく持っていないので、何を確認し何を確認しないか、どういう形式で報告するかを書かないと、報告の粒度が毎回ぶれます。

「呼ばれない」「空振りする」が起きる、仕組み上の理由

症状は大きく3つに分かれます。①/agents の一覧にそもそも出てこない、②一覧には出るが自動で呼ばれない、③呼ばれるが報告が薄い。原因はそれぞれ違うので、対処も別々になります。

①はファイルが読み込まれていない状態で、原因の多くは置き場所の間違いか、YAML の書式エラーです。とくに description に「レビュー: 差分を確認します」のようにコロンと半角スペースを含めると、YAML はそこをキーと値の区切りとして解釈するため、フロントマター全体の解析に失敗します。このときエラーは表示されず、単に一覧に現れません。

②は description の情報不足です。委任の判断はその文面だけを見て行われるので、「いつ使うか」が書かれていなければ判断のしようがありません。

③はコンテキスト分離が原因です。メインの Claude が「レビューして」とだけ書いて委任すると、サブエージェント側は対象ファイルも判断基準も知らないまま作業を始めるため、返ってくるのは当たり障りのない一般論になります。

ここまでが原因の説明です。以降の有料部分では、①〜③をそれぞれ特定して直す手順を扱います。

  • 置き場所を決める：プロジェクト用とユーザー用、どちらに置くか
  • /agents で読み込まれているか確認する：ここが最初の切り分け点
  • tools の書き方：ツール名は正確な文字列で、大文字小文字も一致させる
  • claude コマンドから実行して切り分ける：対話に頼らない確認方法
  • tools と permissions は別レイヤー：コマンド実行の許可が通らない理由
